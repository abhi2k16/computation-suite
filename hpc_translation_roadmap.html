Performance & HPC Translation Roadmap

computation-suite (fea_engine + rom_engine) — scaling to large problems
Written 2026-08-27, following the Phase 4 (certified error bounds) work. GPU addendum (Section 6), hybrid-package/auto-dispatch addendum (Section 7), and data-pipeline diagram (Section 8) added 2026-09-02. For future reference — revisit before starting any large-scale model or a language port.
TL;DR: Don't translate the package yet. Profile a realistically large model first to find the actual bottleneck. When the time comes, the right move is almost certainly a compiled core + Python bindings hybrid (the pattern deal.II, FEniCS, MFEM, and libMesh all use) — not a full rewrite. rom_engine's reduced-space math is already fast in any language, by design; if translation is ever needed it targets fea_engine's full-order assembly/solve, and specific full-order operations inside rom_engine like scm.py's reference-point SVD. GPU (Section 6) is a further-out option on top of that compiled core, worth it only once profiling shows the bottleneck at a scale — roughly 10&sup5;+ dof — where GPU parallelism actually pays for its overhead.

1. Why this isn't a "translate everything" problem

A reduced-order model's whole point is that online queries operate on a small basis (n_modes in the tens, not n_dof). pod.py/galerkin.py/affine.py's reduced-space operations — O(Q · n_modes²) on a 10×10 or 30×30 matrix — are already microseconds in numpy. Compiling that code wouldn't meaningfully speed it up; the dimension it runs at is the reason it's fast, not the language.

Performance work should be scoped by where full-order-sized cost actually lives:

ComponentCost profileStatus
rom_engine online queries
(pod/galerkin/affine, reduced space)		 O(Q · n_modes²) — independent of n_dof already fast, any language
fea_engine assembly
(element loop → K, M, C)		 scales with mesh size; Python element loops are the classic FE bottleneck likely bottleneck at scale
fea_engine full-order solves
(training snapshots, ground truth)		 O(n_dof³) dense, or sparse-solver-dependent bottleneck if K/M are dense
scm.py add_reference()
(full SVD of A(ω))		 O(n_dof³), per reference point, offline bottleneck at scale — numerical fix, not just language

2. Before touching a compiler: cheaper fixes

Several of these are pure-Python changes that may remove the need for a language switch entirely, or at least push the threshold where one becomes necessary much higher.

Sparse instead of dense matrices

If K/M/C are currently dense numpy arrays, that alone caps realistic problem size well under ~10&sup5; dof regardless of what language does the math — real FE matrices are overwhelmingly sparse. Switching to scipy.sparse + a real sparse solver (SuperLU/UMFPACK, already wrapped by scipy.sparse.linalg) is likely the single biggest win available, and it's Python-only.

JIT/compile just the element loop

If assembly is a Python for loop over elements, numba's @njit can often get most of C's speed on that loop with a small, local code change — no build system, no binding layer, no second language to maintain.

Fix scm.py's reference-point cost numerically

add_reference()'s full O(n_dof³) SVD to get just the smallest singular value is wasteful at scale in any language — the fix is switching to scipy.sparse.linalg.svds (or a Lanczos/shift-invert iterative method) to get only the smallest singular value, not the whole decomposition. This is a numerical-method change, independent of the translation question.

3. Profile before deciding anything

Run a realistic model (suggest 10,000–50,000 dof) through fea_engine's assembly and solve, with timing broken out by stage: assembly, factorization/solve, and (if used) rom_engine offline training. The bottleneck's location determines the fix — sparse matrices, Numba, or a compiled kernel are different answers to different problems, and guessing wastes effort.

Given this project's research/prototyping style — heavy iteration, validation against ground truth, documentation-first — Julia is worth serious consideration specifically because it avoids maintaining two codebases and a binding layer. But it's also the option that most changes the project's character, so it shouldn't be the default answer without the profiling step above justifying it.

5. Phased roadmap

PHASE 1

Profile a large model

Build/import a 10k–50k dof mesh in fea_engine. Time assembly, solve, and (if relevant) ROM offline training separately. This determines everything below — do not skip.

PHASE 2

Cheap, Python-only fixes

Sparse K/M/C via scipy.sparse; Numba-JIT the element assembly loop if it's the bottleneck; replace scm.py's full SVD with svds/iterative smallest-singular-value extraction. Re-profile after each change — this phase alone may be sufficient for the target problem size.

PHASE 3

Decide on a compiled core — only if Phase 2 isn't enough

Choose C++, Rust, or Julia per Section 4, based on target scale and how much of a two-language architecture is acceptable. Scope the port to fea_engine's assembly + full-order solve only — not rom_engine's reduced-space code, which doesn't need it.

PHASE 4

Compiled kernel + Python bindings

Keep rom_engine, orchestration, greedy training, testing, and docs in Python. Expose only the compiled assembly/solve kernel via pybind11/nanobind (C++), PyO3 (Rust), or PythonCall (Julia). This preserves the existing pytest-against-fea_engine validation culture and the docs/examples workflow this project already relies on.

6. GPU acceleration — a further-out, conditional option

C++ (and Rust, and Julia) can all target GPU — this section is about whether and when it's worth it here, not whether it's possible. It's a bigger commitment than the compiled-core question in Section 4, so it's deliberately kept separate rather than folded into that decision: choosing C++/Rust/Julia is about language; choosing GPU is about hardware architecture, and the two decisions don't have to be made together.

Where it would and wouldn't help here

GPUs win on a large number of small, independent, regular operations. Two parts of this codebase's cost profile fit that shape:

ComponentGPU fitWhy
fea_engine element assembly
(element loop → K, M, C)		 good fit, at scale thousands–millions of small, independent per-element matrix computations — embarrassingly parallel
fea_engine sparse solve
(iterative/Krylov, not direct)		 good fit, at scale sparse matrix-vector products are memory-bandwidth-bound, and GPU bandwidth is typically 10–20× a CPU's
fea_engine direct sparse factorization
(SuiteSparse/UMFPACK, Section 2's own fix)		 poor fit GPU direct sparse factorization is far less mature than GPU iterative solvers — going GPU here usually means switching solver strategy too (direct → Krylov + GPU-friendly preconditioner, e.g. algebraic multigrid), not just recompiling
rom_engine reduced-space queries
(pod/galerkin/affine, 10×10–30×30)		 actively harmful a single kernel launch costs more than this entire computation takes on CPU — would make it SLOWER, not faster; Section 1's "already fast, any language" verdict applies even more strongly against GPU

Toolchain options

CUDA (NVIDIA-only, most mature FE/linear-algebra ecosystem: cuSPARSE, cuSOLVER, AmgX for GPU algebraic multigrid), HIP/ROCm (AMD's CUDA-alike), or a portability layer — SYCL/oneAPI or Kokkos — that compiles one source to multiple vendor backends. Usefully, this doesn't necessarily mean a new library stack on top of Section 4's choices: PETSc and Trilinos, both already named there, ship GPU-enabled matrix/vector types and GPU-aware Krylov solvers on top of their existing CPU APIs, so adopting them is turning on a backend rather than adopting a wholly separate toolchain.

Complexity, relative to the CPU compiled-core port in Section 4

Meaningfully higher, not a small increment on top of it:

  • a different programming model — explicit kernels, explicit host/device memory management, and a data-layout sensitivity (coalesced memory access) that has no CPU analog and is easy to get wrong on the first pass
  • the direct-solver-to-iterative-solver push noted in the table above is a numerical-methods decision, not just a translation — it can change convergence behavior and needs its own validation against fea_engine's existing ground-truth-comparison test culture
  • vendor lock-in (CUDA) vs. an added portability layer (Kokkos/SYCL) to avoid it — either way, more toolchain surface to maintain than a CPU-only compiled core
  • development and CI both need GPU hardware, which most local setups and many CI runners don't have by default

CPU and GPU together

Standard, not exotic — this is how PETSc and Trilinos are already built. The usual split: CPU handles orchestration, mesh/sparsity-pattern setup, and I/O; GPU handles the parallel numerical kernels (assembly, matvecs, solver inner loops). At full HPC scale this extends to multiple CPU nodes plus multiple GPUs over MPI. The main design discipline is minimizing host↔device data transfers (PCIe/NVLink bandwidth is much lower than either device's own internal bandwidth) — keep data resident on the GPU across as many solver iterations as possible rather than shuttling it back and forth every step.

PHASE 5 (CONDITIONAL)

GPU-accelerated fea_engine solve

Only pursued if Phase 1's profiling, re-run at the target scale after Phases 2–4, still shows the bottleneck in sparse assembly/solve at a scale (roughly 10&sup5;+ dof) where GPU parallelism plausibly pays for its overhead. Turn on PETSc's or Trilinos's existing GPU backend for Mat/Vec types and Krylov solves first — before writing any custom CUDA/HIP kernel — since that's a configuration change on top of the Phase 3/4 compiled core rather than new code. Scope stays exactly as narrow as Phase 3/4's: fea_engine's assembly and full-order solve only. Never rom_engine's reduced-space code — see the table above.

7. One package, both languages — and letting the code choose

Section 4's "compiled core + Python bindings" recommendation and Section 6's GPU backend are both special cases of a more general question: can Python and C++ live in the same installable package, with the package itself deciding which path to run per call? Yes — this is not unusual architecture. numpy/scipy, pandas, and PETSc4py are all exactly this: a Python package with a compiled core, shipped together as one pip install.

Packaging shape

fea_engine stays a normal Python package. An OPTIONAL compiled extension module (built with pybind11 or nanobind — see Section 4) sits alongside it, e.g. fea_engine._core, exposing just the hot functions: element assembly, the sparse solve. The existing pure-Python implementations of those same functions remain in the package as the fallback, not deleted. One package, one test suite, one install command; the compiled piece is an accelerant a caller can be missing (no C++ toolchain, wheel not built for their platform) and still get correct — just slower — results.

Which path is efficient — depends on problem size, not a fixed answer

For small problems (a few hundred–thousand dof, or anything in rom_engine's reduced-space math — the O(Q·n_modes²) case from Section 1), pure Python/numpy is already fast, and crossing into compiled code can cost MORE than it saves: every call across the Python↔C++ boundary means marshalling numpy arrays into C++ structures and back, a roughly constant cost independent of problem size. For large problems (tens of thousands of elements and up), the Python interpreter's per-element overhead in an assembly loop dominates, and the compiled path wins by a growing margin as size increases. There is a genuine crossover point in between — not something to guess at, but exactly what Phase 1's "profile before deciding" is for, applied per-function instead of once for the whole package.

Letting the algorithm decide — real precedent already in this codebase

rom_engine.nnm's jacobian="auto" argument already does this kind of runtime dispatch (falls back to numerical differencing when an analytic Jacobian isn't available), and this project's approach to SCM vs. SCM-LP or one-sided vs. two-sided Krylov is consistently "measure both, let the caller see the trade-off" rather than silently picking one. The same pattern extends naturally to a Python/C++ dispatch, in increasing order of sophistication:

StrategyHow it worksTrade-off
Fixed size threshold if n_elements > N: call compiled path else: pure Python simplest, matches the existing jacobian="auto" convention closely; N is a guess unless it comes from profiling
Calibrated threshold benchmark both paths once (first use, or a small setup step) on the actual machine, cache the crossover point more robust — the right N depends on CPU/memory bandwidth and whether the extension was even built for this platform, not a universal constant
Feature-based dispatch decide on sparsity pattern, condition number, or GPU availability (Section 6), not just raw size most general, most implementation effort; closer to how PETSc lets solver backend depend on matrix properties

Whichever level is chosen, both paths need to be validated against EACH OTHER, not just independently against ground truth — the same test suite should confirm the compiled and pure-Python results agree to numerical precision, so "auto" never means "trust it and hope." This is the same validation discipline every other dual-path decision in this project already follows (one-sided vs. two-sided Krylov, SCM vs. SCM-LP, natural-parameter vs. pseudo-arclength NNM continuation).

Where this fits the phased plan: the dispatch layer is a thin addition on top of Phase 4 (compiled kernel + Python bindings already exist by then) — add the size/feature check and the cross-validation tests once both paths are built, rather than designing the dispatch logic before there's a second path to dispatch to.
