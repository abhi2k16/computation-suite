How fea_engine and rom_engine couple to approach a Reduced-Order Model (ROM) problem

computation-suite — general-purpose module interaction reference, covering every reduction route currently in the package and the optional machine-learning ("torch") layer several of them can use.

fea_engine is a full-order finite element package: it turns a mesh, a material description, and boundary/loading conditions into the actual matrices and solutions of a structural mechanics problem — stiffness, mass, and damping matrices; static, modal, harmonic, and time-stepping solves; linear and geometrically/materially nonlinear elements. Solving the full-order problem directly is accurate but can be slow, especially when the same structure has to be re-solved many times (a parameter sweep, an optimization loop, a real-time control application, a Monte Carlo uncertainty study). rom_engine is a collection of reduced-order modeling (ROM) techniques that build a much smaller, much faster stand-in model from a handful of full-order results, so that only a FEW expensive full-order solves are ever needed, and everything after that runs at a fraction of the cost.

The key design decision that shapes everything below: the two packages are deliberately decoupled at the code level. None of rom_engine's reduction logic imports fea_engine or knows it exists — every function takes plain numpy arrays (a stiffness matrix, a mass matrix, a set of snapshot solutions) or a plain Python callable (a function that, given a load, returns a displacement) as its input. fea_engine is the thing that PRODUCES those arrays and callables from a real structural model; rom_engine only ever CONSUMES them. This means every reduction technique in rom_engine is equally usable with matrices or solvers that come from a completely different finite-element package, a hand-built toy problem, or measured experimental data — fea_engine is simply the one source this project's own tests and examples happen to use to build realistic, checkable inputs.

Glossary — terms used throughout this document

Full-order model (FOM). The actual, physically detailed structural model — the real mesh, the real number of degrees of freedom (often thousands to millions), the real stiffness/mass/ damping matrices. "Full-order" distinguishes it from the much smaller reduced-order model built to approximate it.
Reduced-order model (ROM). A much smaller mathematical stand-in for the full-order model, built so that evaluating it (solving it for a new load, a new frequency, a new time step) costs far less than solving the full-order model again, while still capturing the behavior that actually matters.
Snapshot. One full-order solution (a displacement field, a frequency-response sample, ...) computed by actually solving the FOM once, at one specific set of conditions. Reduction techniques are built from a collection of snapshots.
Reduced basis / mode shapes. A small set of "shape" vectors (each the same length as the full-order displacement vector) chosen so that the true response can be well approximated as a combination of just these few shapes, each scaled by its own small "reduced coordinate." Reducing the problem then means solving for those few scale factors instead of every individual degree of freedom.
Offline / online split. The organizing idea behind almost every technique below: do the expensive work (building the reduced basis, projecting the full-order matrices onto it) ONCE, offline; then answer every subsequent query (a new load case, a new frequency, a new time step) cheaply, online, using only the small reduced system, never touching the full-order model again.
Intrusive vs. non-intrusive. An "intrusive" technique needs direct access to the full-order model's own matrices (stiffness, mass, damping) to build its reduced model. A "non-intrusive" technique only needs INPUT/OUTPUT data — e.g. a set of (load, response) pairs, or a set of measured frequency-response points — and never needs the matrices themselves. Non-intrusive techniques can be built from experimental measurements, not just simulation.
Newton-Raphson iteration. The standard numerical method for solving a nonlinear equation: starting from a guess, repeatedly using the equation's own local slope (its "Jacobian," see below) to compute a correction, until the equation is satisfied to within a small tolerance.
Jacobian. The matrix of first derivatives of a (possibly nonlinear) function with respect to its inputs — how much each output changes for a small change in each input. Needed by Newton-Raphson iteration and by gradient-based training.
Automatic differentiation. Software machinery that computes exact derivatives (gradients, Jacobians) of an arbitrarily complicated computation automatically, without a person deriving the calculus by hand. This is what makes training a neural network practical (see "the torch switch" below) and is also used directly on plain finite-element and reduced-order computations in a few places in this project, with no neural network involved at all.

The two basic shapes of the coupling boundary

Every route below hands data across the fea_engine → rom_engine boundary in one of exactly two shapes, depending on whether the underlying structural model is linear or nonlinear.

Shape 1 — plain arrays, for linear models

Reading shape 1: offline vs. online

The whole point of this coupling shape is to spend fea_engine's expensive full-order machinery (mesh, assembly, factorized solves) only during an OFFLINE training phase, then never touch it again during the many cheap ONLINE queries a real use case needs.

  • Offline (top four rows, run once, expensive): fea_engine builds the mesh and assembles the stiffness/mass/ damping matrices. Those arrays hand off to rom_engine, which either (a) fits a reduced basis from a fixed grid of full-order snapshots (the POD route), or (b) runs a weak-greedy loop, which adaptively decides which conditions are worth an expensive full-order solve by watching where its own cheap error indicator is largest — the dashed feedback arrow. Either way, the resulting reduced basis plus the original full arrays get projected ONCE. This whole offline stage — the mesh-geometry precompute, the assembly itself, and (for a large enough system) the iterative linear solve — is exactly where fea_engine's own GPU-optional backend="torch" switch now reaches (Wave 9 addendum): still plain NumPy/SciPy by default, still handing rom_engine the SAME plain arrays either way, just optionally faster to produce on a large model. rom_engine's own code downstream of the handoff never knows or cares which backend built them.
  • Online (bottom rows, run many times, cheap): new queries are answered using only the small projected system — no mesh, no assembly, no full-order solve, ever. The certified-bound route sits alongside and turns the residual into a genuinely proven error bound using the same projected components, at the same online cost.
  • Validation (long dashed loop on the left): this is NOT part of the production path — it's how the automated test suite checks that the online predictions are actually right, by calling fea_engine's own independent solvers as ground truth.
Naming discipline shows up in the diagram on purpose: an error estimate or an error indicator is explicitly UNcertified (cheap, useful for ranking or deciding where to add training data, but not provably correct); a certified error bound (from the Successive Constraint Method route) is the one number in the whole package that's rigorously proven to never undershoot the true error — and it's also the narrowest/most limited one in practical reach, a real trade-off, not a free upgrade.

Shape 2 — a plain callable, for nonlinear models

Shape 1's plain stiffness/mass/damping arrays only make sense for LINEAR structural models — a nonlinear element (large deformation, a nonlinear material) doesn't have one fixed stiffness matrix at all; the relationship between load and displacement bends. For these models, rom_engine couples to fea_engine through a single, much narrower interface instead: a plain Python callable, conceptually fom_solver(load) -> displacement, that wraps whichever nonlinear solver the caller wants. The reduction code itself never imports fea_engine or even knows it exists — the SAME code is equally happy driven by a hand-wrapped call into any other FE package, or by no FE package at all (a purely analytic stand-in function, as several of this project's own tests use).

The offline/online split is the same idea as shape 1, just at a different scale: generating training pairs means calling the nonlinear solver callable — a genuine full nonlinear finite-element solve — once per training sample (expensive, offline). Once a surrogate is fit, every subsequent evaluation is a small, reduced-dimensional solve with no mesh, no assembly, and no fea_engine involvement at all — the online query stays exactly as decoupled as shape 1's.

The torch switch — how the optional machine-learning layer works

Most of rom_engine needs nothing beyond numpy and scipy. A handful of the newer, more data-driven routes — the neural-network flavor of the nonlinear surrogate above, a trainable correction term, an operator that learns a whole excitation-to- response mapping, and a couple of others described below — are built on small neural networks, and training a neural network needs automatic differentiation: software that computes the gradient (the direction that reduces a training loss) of a complicated computation, so the network's internal numbers can be adjusted automatically rather than by hand. rom_engine uses PyTorch (referred to here, and in the code, simply as torch) for this. PyTorch is a substantial optional dependency, and not every user of this package needs it, so it is treated as strictly opt-in: nothing in the package requires it just to import or use the non-neural-network routes.

The consequence for how the code is written: every function or class that only needs ordinary linear algebra (matrix multiplies, eigenvalue problems, least-squares fits, numerical integration) is written ONCE and never checks whether torch is present — it works identically either way. Only the specific pieces that need automatic differentiation to train a neural network's internal weights are placed behind the switch. Calling one of those without torch installed raises an immediate, clearly worded error explaining what to install and, in most cases, which non-neural-network alternative already covers the same use case — never a confusing failure buried deep inside a computation.

What actually needs the torch switch, across the whole package: the neural-network flavor of the nonlinear surrogate model; a trainable correction term added into a reduced equilibrium equation; the ensemble uncertainty-quantification tool, when it is wrapped around that neural-network surrogate specifically; the excitation-to-response operator; the bias-correction network inside the discretization-robust encoder/decoder; and the parameterized latent-ODE model (all described in the routes below).

Everything else needs only numpy/scipy, with no optional dependency at all: proper orthogonal decomposition, Galerkin projection, affine decomposition, frequency-domain reduction, greedy adaptive training, certified error bounds, non-intrusive system identification from frequency-response data, Krylov-subspace and balanced-truncation style reduction, harmonic-balance nonlinear normal modes, the radial-basis-function and polynomial flavors of the nonlinear surrogate, nonlinear time integration, design-of-experiments sampling, and dataset diagnostics.
A second, unrelated use of torch: a few routes — balanced truncation and optimal Hankel-norm approximation in category C below, and several of fea_engine's own assembly/solve stages that feed every route on this page — also gained an optional backend="numpy" (default, unchanged) / backend= "torch" + device= switch. This is not the automatic-differentiation usage described above: no training, no neural network, no gradient anywhere in these paths. It is the SAME matrix-multiply/Lyapunov-solve/SVD-style linear algebra these routes always did, just optionally dispatched to a GPU tensor library instead of NumPy/SciPy when a model is large enough for that to pay off. Every one of these routes still runs, unchanged, with no torch installed at all — the GPU-optional badge below marks this second, narrower kind of torch dependency wherever it appears, to keep it visually distinct from the torch badge's actual meaning (training requires torch). See fea_engine/docs/consolidated_future_roadmap.md's Wave 9 addendum (items 135-138) for the full validation record.

Every route through rom_engine, by category

"Route" here means a distinct path from full-order data to a usable reduced model — a specific combination of what kind of structural model it applies to (linear or nonlinear), what data it needs (intrusive access to matrices, or only input/output samples), and what it optimizes for (raw speed, provable error bounds, accuracy across a whole frequency range vs. near one operating point, generalizing to conditions never explicitly trained on, ...). The package does not pick one "best" route — different structural problems and different accuracy/speed/ certification needs call for different ones, and several can be applied to the same problem side by side for comparison.

A — Linear, intrusive, projection-based reduction
Needs direct access to the stiffness/mass/damping matrices. The classical starting point for reduced-order modeling.
RouteWhat it answersHow it works, in plain terms
Proper Orthogonal Decomposition (POD) Given a set of full-order solutions, what's the smallest number of "shapes" that captures most of how they vary? Runs a singular value decomposition on the collected snapshots to find the directions of greatest variation, in order of importance. A "mass-weighted" variant uses the mass matrix so the resulting shapes come out orthogonal in the same physically meaningful sense as classical vibration mode shapes. needs matrices
numpy only
Galerkin projection Given a reduced basis, how do I get a small system of equations that approximates the full one? Projects the full-order matrices onto the reduced basis (a standard linear-algebra operation: sandwich each matrix between the basis and its own transpose), for both static equilibrium and vibration (eigenvalue) problems. needs matrices
numpy only
Affine parametric decomposition My matrices depend on a design parameter (a thickness, a material property, a frequency) — how do I avoid re-projecting from scratch every time that parameter changes? When the matrix can be written as a sum of a few fixed "component" matrices, each scaled by a simple function of the parameter, only the FIXED components need to be projected once (offline); recombining them for a NEW parameter value (online) is then just a cheap weighted sum of small, already-reduced pieces — the foundational offline/online split for "many-query" problems (sweeps, optimization, uncertainty studies). needs matrices
numpy only
Frequency-domain reduction How do I get a fast harmonic (steady-state oscillating) response across a whole sweep of driving frequencies? The harmonic-response equation is naturally affine in the driving frequency, so this route is simply the affine-decomposition idea applied specifically to that equation, using either a vibration-mode basis or a POD basis built from frequency-response snapshots. needs matrices
numpy only
Greedy adaptive training Which training conditions actually deserve an expensive full-order solve? Rather than a fixed grid of training points chosen up front, this route repeatedly checks a cheap error indicator across the whole condition space and only spends a real full-order solve at the single worst-represented point each round ("weak greedy"), growing the basis where it is actually needed. needs matrices
numpy only
Certified error bounds (Successive Constraint Method) Can I PROVE the reduced answer is within some known distance of the true one, not just estimate it? Computes a rigorously certified lower bound on a quantity (the smallest singular value of the system matrix) that turns an otherwise uncertified residual into a provable upper bound on the true error. Available as a simplified, wider-reach version and as the full classical linear-programming-based version, which is narrower in practical reach but the more literal implementation of the original method. needs matrices
numpy only
B — Non-intrusive system identification
Never needs the stiffness/mass/damping matrices at all — only input/output data, which can come from measurements, not just simulation.
RouteWhat it answersHow it works, in plain terms
Data-driven modal identification (Loewner framework) I only have measured or simulated frequency-response DATA POINTS — no matrices at all. Can I still recover the natural frequencies, damping, and mode shapes? Builds a pair of matrices (a "Loewner pencil") directly from interpolating the given frequency-response samples; the generalized eigenvalues of that pencil ARE the system's identified natural frequencies and damping ratios, with mode shapes reconstructed from the same data. Also deliberately left NumPy/SciPy-only, same reasoning as Krylov-subspace moment matching below: the pencil is sized by the NUMBER OF INTERPOLATION POINTS, typically small, so there is no GPU-worthwhile computation here either. data only
numpy only
Cross-model stability screening How do I tell a genuine structural mode apart from a numerical artifact of picking too large a model order? Builds many independent identified models from random subsets of the available frequency data, then keeps only the eigenvalues that show up consistently, tightly clustered, across most of them. data only
numpy only
C — Classical control-theory-style reduction for linear systems
Intrusive (needs the matrices), but optimizes for a fundamentally different accuracy trade-off than a vibration-mode basis: exactness near one operating point, or accuracy across a whole input/output pair regardless of frequency.
RouteWhat it answersHow it works, in plain terms
Krylov-subspace moment matching I mainly care about accuracy near ONE specific operating frequency — can I get a reduced model that matches the true response exactly there, cheaply? Builds a reduced basis, from repeated use of a single matrix factorization, chosen so the reduced model's frequency response matches the true one's local (Taylor-series) behavior exactly at one expansion point, with accuracy tapering off farther away. A "two-sided" variant matches roughly twice as many terms from the same reduced size, at the cost of a more fragile construction. Deliberately left NumPy/SciPy-only — unlike balanced truncation's dense state-space linear algebra above, this route's per-generation systems are already small enough that GPU dispatch has no real work to accelerate. needs matrices
numpy only
Second-order Krylov reduction Same question as above, but without first doubling the number of unknowns by converting to a first-order form. The same moment-matching idea, built directly from the mass/damping/ stiffness matrices in their natural second-order form, avoiding the state-space doubling the plain Krylov route needs. needs matrices
numpy only
Balanced truncation ⚡ GPU-optional I care about accuracy across the WHOLE frequency range for a specific set of inputs/outputs, not just near one point — and I want a provable worst-case error bound. Ranks the reduced states by how strongly they simultaneously affect the chosen inputs and outputs (via two matrix equations, one per direction), keeps the most important ones, and comes with a real, proven worst-case bound on the reduction error. A "singular perturbation" variant fixes balanced truncation's one known weak spot (it is slightly wrong at zero frequency / steady state); a "frequency-weighted" variant trades accuracy in a chosen frequency band against accuracy elsewhere. All three optionally dispatch their two dense matrix-equation solves plus the balancing SVD to a GPU (backend="torch", no training involved — see the GPU-optional callout above). needs matrices
numpy default
GPU-optional
Optimal Hankel-norm approximation ⚡ GPU-optional Is there a reduced model that is PROVABLY the best possible one of its size, in a specific rigorous sense? A more advanced construction (built on the same balancing machinery balanced truncation uses) that produces a reduced model with the smallest possible worst-case error, in a technical measure called the Hankel norm, among every model of that size — not merely a good one. Reuses balanced truncation's own GPU-optional balancing step for its (genuinely expensive) main computation and its own empirical self-check; the Schur-decomposition/Sylvester-equation construction that follows stays NumPy/SciPy-only, since it operates on the already-small reduced system regardless of GPU availability. needs matrices
numpy default
GPU-optional
Passivity check Does my reduced model still respect basic energy conservation? Checks whether a reduced model preserves "passivity" — the physical property that a real structure never generates energy out of nothing. Some reduction methods can produce a model that is numerically close to the truth but technically not passive, which can make a simulation coupling that reduced model to something else behave unphysically or become unstable; this route checks for that directly rather than assuming it can't happen. needs matrices
numpy only
D — Nonlinear surrogate reduced-order modeling
For structural models whose stiffness genuinely depends on the deformation itself. Uses shape 2's plain-callable coupling from the section above.
RouteWhat it answersHow it works, in plain terms
Radial-basis-function (RBF) surrogate Given a handful of (reduced state, nonlinear force) training pairs, how do I interpolate the nonlinear force smoothly at any NEW reduced state? Builds a smooth interpolant of the nonlinear restoring force as a function of distance from each training point — no iterative optimization needed, just a linear solve. callable-based
numpy only
Polynomial surrogate Same question, but with a form that stays well-behaved when extrapolated slightly beyond the training range. Fits the nonlinear restoring force as a quadratic-plus-cubic polynomial of the reduced coordinates by ordinary least squares — a closed-form regression, matching the classical form nonlinear structural- dynamics reduction techniques in the literature use. callable-based
numpy only
Neural-network surrogate ⚡ torch Same question again, when the true relationship is complex enough that a small neural network fits it better than a fixed polynomial or interpolant form. Trains a small feedforward neural network on the same (reduced state, nonlinear force) training pairs, using the torch switch described above — same input/output shape as the other two surrogates, so it is a drop-in alternative, not a separate code path. callable-based
torch
Reduced nonlinear time integration Given any of the three surrogates above, how do I march the reduced system forward in time? A standard structural-dynamics time-stepping scheme (Newmark-beta), generalized to accept any of the three surrogate force models, with several different strategies for folding the nonlinear force into each step — from a cheap frozen/lagged estimate up to a genuine Newton-Raphson solve every step for guaranteed convergence at higher cost. callable-based
numpy only
Harmonic balance / nonlinear normal modes What is the structure's own steady-state PERIODIC vibration response — and how does its natural frequency shift with amplitude, the signature of nonlinear behavior a linear vibration analysis can't see at all? Represents the periodic response as a truncated Fourier series (harmonic balance) and solves for its coefficients directly, rather than time-marching to steady state; traces out how the resonant frequency changes with vibration amplitude (a "backbone curve") using continuation, including a more advanced form of continuation able to trace through an amplitude fold that a simpler continuation scheme cannot pass. callable-based
numpy only
E — Neural-operator and trajectory-level, data-driven reduction
The newest and most machine-learning-heavy routes. All torch-gated. Each generalizes across a different axis that every route above is tied to: a specific excitation shape, a specific mesh resolution, or a specific physical parameter value.
RouteWhat it answersHow it works, in plain terms
Excitation-to-response operator ⚡ torch Every surrogate in category D predicts an instantaneous force from an instantaneous state, and has to be separately time-marched for every new load case. Can ONE trained model instead map a WHOLE excitation time history directly to the WHOLE response time history — including for excitation shapes it never saw during training? A compact "Fourier Neural Operator": a neural network that operates in the FREQUENCY domain, learning an independent filter for each retained frequency component of the input signal, plus an ordinary (time-domain) skip connection. Can optionally be trained with an extra penalty term that checks its own predicted trajectory against the true reduced equation of motion (using finite differences of the prediction itself), which this project's own testing found materially improves how well it generalizes to an unseen excitation, beyond fitting the training waveforms alone. callable-based
torch
Discretization-robust encoder/decoder ⚡ partly torch An ordinary reduced basis (from POD) is tied to the exact mesh it was built from — it cannot even be evaluated on a different mesh resolution. Can a reduced representation be built once and reused across DIFFERENT mesh resolutions? Represents a normally discrete set of basis shapes as a mathematically CONTINUOUS field using an interpolation scheme, so encoding a new full field into reduced coordinates, and decoding reduced coordinates back to a full field, can both be evaluated at ANY query coordinates — not just the original mesh's own node locations. This core piece needs no neural network at all. An optional add-on neural network can then learn a small bias correction on top of the plain (linear) encoding, which does use the torch switch. data-based
core: numpy only
bias correction: torch
Parameterized latent ordinary differential equation (ODE) ⚡ torch What if the SAME structural setup is run repeatedly with a different value of some physical parameter each time — a load amplitude, a material or geometric property — and I want one model that predicts the response for a NEW parameter value directly, not by re-fitting a surrogate for each one? Learns the reduced dynamics directly as an ordinary differential equation whose right-hand side is a small neural network, conditioned on the physical parameter (which is held fixed within one training trajectory but varies across the training set), integrated forward in time with a from-scratch, verified 4th-order Runge-Kutta scheme. Trained with "curriculum learning": the model is first only required to get the first few time steps right, then the length of trajectory it must get right is progressively extended as it improves — training directly on the FULL trajectory length from the start tends to be numerically unstable for this kind of model. callable-based
torch
F — Supporting infrastructure used across every route
Not reduction techniques themselves — tools that make building, checking, and trusting any of the routes above more systematic.
RouteWhat it answersHow it works, in plain terms
Design-of-experiments sampling When I have to choose a limited number of expensive training conditions (loads, parameter combinations), how do I spread them out well rather than clustering by chance? A general-purpose "optimal Latin hypercube" sampler: spreads a chosen number of points across a parameter space so they are well separated from each other (better coverage than plain random sampling), used to choose training conditions for several of the routes above. numpy only
Dataset diagnostics Before spending time training a surrogate, does my training data actually cover the space well? How many independent directions of variation does it really contain? Which input parameters matter most to the output? Checks the sampled parameter combinations for coverage gaps, estimates the effective dimensionality of the training data (how many independent directions of variation it contains), and uses a cheap approximate model to estimate which inputs matter most to the output (a sensitivity analysis). numpy only
Ensemble uncertainty quantification How confident should I be in a surrogate's prediction at a given input? Trains several independently-initialized copies of the same surrogate model on the same data, and reports how much they disagree with each other as a cheap proxy for confidence: the more the independently-trained copies disagree at a given input, the less that input resembles anything the model actually learned from. numpy only for most model types;
torch when wrapped around the neural-network surrogate specifically
Differentiable trainable correction terms ⚡ torch Rather than replacing a surrogate model entirely, can I train a small CORRECTION term that gets added directly into an already-existing reduced equilibrium equation, to nudge its predictions toward reference data? Adds a trainable correction term into the reduced equilibrium equation and calibrates it using the same automatic-differentiation machinery used to train neural-network surrogates — so the correction can be tuned by directly minimizing how much it disagrees with reference data, rather than being fit in isolation first and inserted afterward. torch for the trainable version; the underlying residual computation itself is numpy only
Cross-route validation Do multiple of the routes above actually AGREE with each other, and with an independent reference, when applied to the same real structural problem — not just pass their own isolated tests? Runs several routes together on one shared structural model and checks them against each other: e.g. two different time-integration schemes solving the SAME reduced equation should agree with each other; a basis fit at one mesh resolution should reconstruct a solution computed at a genuinely different resolution to within a documented tolerance. numpy-only core
plus an optional torch-gated extension that also exercises the neural-operator routes

A shared-pattern coupling — not data flow, but a mirrored design

Every route above couples through DATA flowing one way, at solve time: fea_engine computes something, rom_engine consumes it. There is one more, genuinely different kind of coupling between the two packages worth knowing about: in a couple of places, fea_engine and rom_engine each independently implement the exact SAME mathematical pattern — a trainable correction term inserted additively into an equilibrium residual, calibrated by minimizing that residual against reference data — at two different scales (the full finite-element displacement field, versus a handful of reduced modal coordinates). Because rom_engine's own design principle is that fea_engine is a TEST/EXAMPLE dependency only, never a LIBRARY one, the reduced-scale version does NOT import the full-order one, even though the two are a direct mathematical analogue of each other — the same pattern is deliberately reimplemented independently at the smaller scale, rather than shared through an import.

Why not just import the full-order version from the reduced-order package and save the duplication? Because rom_engine's reduced-order machinery is useful to people who never touch a real finite-element mesh at all — it is already driven, in category D above, by a plain solver callable that could come from anywhere. Making the correction- training machinery depend on fea_engine would break that for every user who doesn't need it, to save re-deriving a small amount of already-simple reduced-space math. The missing reduced-scale implicit-adjoint layer is the natural trigger to revisit this boundary, if a future use case needs it.
